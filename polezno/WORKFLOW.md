## 2. Архитектура
- TypeScript, Node 24+, прямой Telegram HTTP API через fetch.
- SQLite WAL: локальная/односерверная V1 без инфраструктуры. PostgreSQL/pgvector — возможный следующий адаптер, не заявлять реализованным.
- Проверяемый поиск по словам для небольшой базы; не называть семантическим.
- config → storage → policy/knowledge → engine → transport/AI worker → runtime.
- Inbox сохраняется до подтверждения polling. Состояние, задания и outbox меняются транзакционно.
- Временные ошибки повторяются; постоянные → failed + административный retry.
- Один polling процесс на БД; вложения через file_id, без бинарных копий.
- Telegram sendMessage не имеет idempotency key: авария между отправкой и записью результата может дать дубль. Документировать.

## 7. Обязательные автоматические проверки
1. Два врача/два DB connections: одно обращение, один победитель.
2. Сообщения до/после claim не теряются.
3. ИИ после /doctor подавляется.
4. Закрытие → новый ID и пустой контекст.
5. Чужой врач не отвечает/не закрывает.
6. Поддельная кнопка из другой группы отклоняется.
7. История/файлы полны; payload без Telegram ID/username/forward-origin.
8. Несколько обращений: reply верен; неизвестный reply не уходит случайному человеку.
9. Повтор update/callback/рестарт не создаёт повторных действий.
10. Outbox после рестарта; 429/500/timeout/403 классифицируются.
11. ИИ уже в outbox отменяется после эскалации.
12. Невалидный каталог отклоняется целиком, старый сохраняется.
13. Пустая база/неизвестный/просроченный товар: нет выдуманных рекомендаций.
14. LLM без источника/чужой ID/URL/дозировка/битый JSON: fallback.
15. Prompt injection не получает прав.
16. First/latest attribution, неправильный payload.
17. Статистика только админу.
18. Timezone/выходной/граница времени/ночной график.
19. Unicode и лимиты текста/caption.
20. Правки/альбомы/неподдерживаемые сообщения.
21. Config/lock/shutdown/health.
